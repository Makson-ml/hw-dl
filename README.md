## 1. Введение

**Цель работы:** освоить развёртывание и настройку распределённого сервиса координации Apache ZooKeeper, а также интегрировать его с координатором расчёта для обеспечения отказоустойчивости, автоматического выбора лидера, восстановления после сбоев (failover) и гарантии согласованности данных.

**Задачи:**
- Поднять отказоустойчивый ансамбль из трёх серверов ZooKeeper
- Проверить кворум, эфемерные узлы и роли серверов
- Интегрировать ZooKeeper с координатором расчёта пар навыков (ДЗ №3, вариант Go)
- Продемонстрировать смену лидера при отказе и восстановление с чекпоинта
- Показать проблему split-brain без защиты и её решение через fencing по эпохе

Ансамбль поднят в Docker на базе официального образа `zookeeper:3.9.6`. Три сервера (`zk1`, `zk2`, `zk3`) связаны через внутренние порты `2888` (peer-to-peer) и `3888` (выборы лидера), клиентские порты `2181–2183` проброшены на хост.

### 2.4. Эфемерный узел

В клиенте `zkCli.sh` был создан эфемерный узел:
create -e /test_coordinator "I_am_alive"

![Создание эфемерного узла](screenshots/05_ephemeral_create.png)

После закрытия сессии клиента (`quit`) и повторного подключения узел исчез:

get /test_coordinator → Node does not exist: /test_coordinator

![Исчезновение узла](screenshots/06_ephemeral_gone.png)

Это демонстрирует механизм, на котором строится обнаружение сбоев координатора: при разрыве сессии эфемерный узел лидера автоматически удаляется, позволяя запасному координатору стать лидером.

## 3. Этап 3: Приостановка лидера без защиты

### 3.1. Сценарий

Запущены две копии координатора расчёта пар навыков (вариант Go) с таймаутом сессии **10 секунд**. Первый координатор (`coord_12224`) стал лидером (эпоха 1) и начал вычисления. Второй (`coord_2300`) ожидал в режиме follower.

### 3.2. Ход эксперимента

1. **15:14:10** — Первый координатор стал лидером, начал обработку файла `vacancies.jsonl` (55 004 037 байт).
2. **15:14:15** — Первый координатор остановлен (Ctrl+C) на отметке **27 233 727 байт** (~49% файла). Эфемерный узел лидера удалён.
3. **15:14:15** — Второй координатор обнаружил исчезновение узла, стал лидером с **эпохой 2**, загрузил чекпоинт и продолжил вычисления с позиции 27 233 727 байт.
4. **15:14:20** — Второй координатор завершил вычисления и **записал результат без защиты**.
5. После повторного запуска первый координатор доделал свой хвост вычислений и **перезаписал результат**.

### 3.3. Время смены лидера

От остановки первого координатора до становления лидером второго прошло **~0 секунд** (эфемерный узел удалился мгновенно при завершении процесса). При сетевом разрыве (без Ctrl+C) задержка составила бы **10 секунд** — таймаут сессии ZooKeeper.

### 3.4. Проблема split-brain

Без защиты по эпохе **оба координатора записали результат**, что приводит к неконсистентности данных.

![Split-brain](screenshots/09_failover_no_fencing.png)

## 4. Этап 4: Приостановка лидера с защитой по эпохе

### 4.1. Сценарий

Тот же эксперимент, но с флагом `--fencing`. Перед записью результата координатор проверяет:
1. Совпадает ли его локальная эпоха с текущей в ZooKeeper
2. Не записан ли результат другим координатором

### 4.2. Ход эксперимента

1. **15:26:29** — Первый координатор (`coord_6104`) стал лидером (эпоха 1), обработал ~43 990 667 байт и был остановлен.
2. **15:26:36** — Второй координатор (`coord_27164`) стал лидером (эпоха 2), загрузил чекпоинт, завершил вычисления и **успешно записал результат**:

Result successfully and safely written (Epoch 2)

3. **15:26:50** — Третий запуск (`coord_27344`, эпоха 3) попытался записать результат, но получил отказ:
   REJECTED: Result already exists in ZooKeeper. Write cancelled to prevent overwrite.

### 4.3. Результат

Защита по эпохе **предотвратила перезапись** актуального результата устаревшими данными. В ZooKeeper остался только один корректный результат от координатора с эпохой 2.

![Отклонение записи](screenshots/08_failover_with_fencing.png)

### 4.4. Совпадение с ДЗ №3

Контрольные числа (частоты синглтонов, пар и троек навыков Go) после восстановления с чекпоинта **полностью совпали** с результатами ДЗ №3, что подтверждает корректность механизма чекпоинтов.

## 5. Ответы на вопросы

### Вопрос 1: Почему серверов три, а не два и не четыре?

ZooKeeper использует **кворумное согласие**: для выполнения записи необходимо большинство серверов, равное `N/2 + 1`.

- **Два сервера:** кворум = 2. При отказе одного остаётся 1 сервер, что меньше кворума. Кластер полностью теряет работоспособность. Отказоустойчивость = 0.
- **Четыре сервера:** кворум = 3. Можно пережить отказ только одного сервера (останется 3 ≥ кворума). Это не даёт преимуществ перед тремя серверами, но требует вдвое больше ресурсов.
- **Три сервера:** кворум = 2. Можно пережить отказ одного сервера (останется 2 ≥ кворума). Это **оптимальный минимум** для обеспечения отказоустойчивости при минимальных затратах.

### Вопрос 2: Почему защиту по эпохе проверяет получатель записи, а не ZooKeeper?

ZooKeeper — это **универсальный сервис координации**, работающий на уровне байтов и версий узлов (ZXID). Он не знает семантики данных приложения и не имеет понятия "эпоха лидера" или "результат вычислений".

Механизм **fencing** реализуется на стороне приложения:
1. Координатор при становлении лидером инкрементирует счётчик эпохи в ZooKeeper и запоминает его локально.
2. Перед записью финального результата координатор сверяет свою локальную эпоху с текущей в ZooKeeper.
3. Если эпохи не совпадают — значит, за время "сна" или сетевой изоляции был выбран новый лидер, и запись старых данных была бы опасной (split-brain).

ZooKeeper предоставляет **примитив** (атомарный счётчик/версию узла), а **логику проверки** реализует само приложение. Это соответствует принципу разделения ответственности: инфраструктурный сервис не должен знать бизнес-логику.

## 6. Выводы

### Технические выводы

1. **Ансамбль из трёх серверов ZooKeeper** обеспечивает отказоустойчивость с кворумом 2 из 3.
2. **Эфемерные узлы** — ключевой механизм обнаружения сбоев: при разрыве сессии узел автоматически удаляется.
3. **Чекпоинты в ZooKeeper** позволяют запасному координатору продолжить вычисления с места остановки лидера.
4. **Без защиты по эпохе** возникает split-brain: оба координатора записывают результат, что приводит к неконсистентности.
5. **С защитой по эпохе (fencing)** устаревшая запись отклоняется, в хранилище остаётся только актуальный результат.
6. **Время смены лидера** определяется таймаутом сессии ZooKeeper (в нашем случае 10 секунд).

### Бизнес-выводы

1. Для production-систем **обязательна** реализация fencing при использовании распределённых координаторов.
2. ZooKeeper — надёжный инструмент для обеспечения согласованности в распределённых приложениях.
3. Механизм чекпоинтов позволяет минимизировать потери вычислений при сбоях.
